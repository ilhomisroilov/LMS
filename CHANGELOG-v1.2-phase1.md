# EduCore LMS — v1.2 Phase 1 (Security & Isolation Foundation)

Status: **implemented & tested** · DB: **PostgreSQL** · 24/24 tests passing

Phase 1 is the spec's hard gate (see `EduCore-LMS-v1.2-Technical-Specification.md`
§19): nothing else proceeds until role-based isolation and auth are bulletproof.
This change set evolves the existing v1.0 backend in place.

## What was built

### Multi-tenant foundation (spec §10)
- New `organizations` + `branches` tables (`app/models/organization.py`).
- `organization_id` (+ optional `branch_id`) added to `users`, `students`,
  `teachers`, `parents`, `groups`, `courses`, `payments`, `attendance`.
- Tenant mixins in `app/core/tenancy.py`.

### Three-layer authorization engine (spec §12)
- `app/core/permissions.py` — role→permission matrix for the six roles
  (super_admin, admin, manager, teacher, student, parent).
- `app/core/authz.py` — `AuthContext`, `require_permission(...)` dependency
  (layer 2), and ownership-scope resolvers like `ensure_student_access` (layer 3).
- Layer 1 (tenant) enforced in repositories: every scoped query filters
  `organization_id`. A teacher only sees assigned students; a student only sees
  itself; cross-tenant access is impossible.

### Hardened authentication (spec §12.1)
- JWT access tokens now carry `org`, `branch`, role and `tv` (token_version).
- Refresh tokens: **rotation + family revocation + reuse/theft detection**;
  only a SHA-256 hash is stored (`app/models/refresh_token.py`).
- `token_version` enables force-logout-all (`/auth/logout-all`).
- **No hidden/default passwords**: invited users have no password until they
  redeem a single-use invite (`/auth/accept-invite`); `/auth/change-password`
  rotates sessions. bcrypt cost = 12.

### Audit log (spec §14.2)
- Append-only `audit_logs` table + `app/core/audit.py` writer, wired into login,
  refresh, reuse-detection, logout, logout-all, password change, invite accept.

### Richer `/me` contract (spec §11.2)
- Returns org, role, **effective permission set**, and linked entities
  (child student ids for parents, group ids for teachers) — drives the
  frontend's role-based nav.

### Database migration (spec §6.5)
- `alembic/versions/aed16a0edc87_v1_2_tenancy_authz_audit_invites.py`
  (chains onto the v1.0 head). Verified to apply on a clean PostgreSQL 16.

## Tests (24 passing, real PostgreSQL)
- `tests/test_security_isolation.py` (new, gating):
  role-matrix sweep, cross-tenant list + by-id isolation, teacher ownership,
  parent blocked from admin endpoints, refresh reuse → family revoked,
  logout-all invalidates access tokens, invited user can't log in,
  invite-accept + change-password flow, audit-log written.
- Existing `test_auth`, `test_modules`, `test_rbac` still pass.

## How to run

```bash
cd backend
pip install -r requirements.txt
# Set DATABASE_URL to your PostgreSQL, then:
alembic upgrade head
python -m app.seed          # seeds 2 orgs (see logins below)
uvicorn app.main:app --reload

# Tests run against an embedded PostgreSQL (pip install pgserver), zero setup:
pip install pgserver pytest httpx
python -m pytest -q
```

Seeded logins: Org A admin `+998901112233 / Admin12345`,
manager `+998901112200 / Manager12345`; Org B admin `+998909990001 / Admin12345`.

## Not yet done (next increments)

  list endpoints (teachers, groups, courses, payments, attendance, dashboard).
  Students + /me + auth are fully scoped and tested; the others currently serve
  the single demo org and need the tenant filter wired in before multi-org use.
- Parent/teacher read routes (e.g. `/me/children`), the learning core (tests,
  roadmap), and the frontend cache-isolation work (spec §13.4).
- For upgrading a *populated* v1.0 DB, the autogenerated migration needs a
  backfill step for the new NOT NULL `organization_id` columns (additive →
  backfill → enforce), per spec §6.5. Fresh deploys apply cleanly as-is.
